# R2b WO-0051 notes: acceptance, pilot notice, onboarding and not-available screens

## Built
- Pages under `apps/web/app/(auth)/`: `accept-terms`, `pilot-notice`, `onboarding`, `not-available` (they answer 404 unless `NEXT_PUBLIC_DATA_BACKEND=supabase`), plus public `/privacy` and `/terms`.
- Each is reached only through `decideRoute` (proxy): `needs_documents` -> accept-terms, `needs_pilot_notice` -> pilot-notice, `needs_onboarding` -> onboarding, `not_available` -> not-available. The forms finish with a fixed `window.location.assign('/')` and the proxy sends the person to the next step.
- `lib/supabase/consent-actions.ts`: `readVersions` (`app.public_setting`), `readSupportedCountries` (`app.supported_countries`), `acceptDocuments` (`accept_documents`), `acceptPilotNotice` (insert into `app.consent_records`), `completeOnboarding` (`complete_onboarding`). All use the caller's session. No server text reaches the screen except fixed messages.
- Notice text: `lib/consent-form.ts` holds the three paragraphs of `legal/PRIVACY-POLICY.md` section 13 and the FR-61 and FR-9 sentences; a test reads the legal file and the FDD and fails if they differ by one character.

## Decisions
1. Versions (the open gap of WO-0050): terms, privacy and notice versions are read from `app.public_setting` on the server when a page renders; the form sends exactly those values. `accept_documents` raises `stale_version`, and the consent insert policy refuses a notice version that is not current, so a page that is out of date gets "Reload the page" and nothing is stored. There are no version constants in the app.
2. Legal documents: link only. `/privacy` and `/terms` are public pages that name the repository file (`legal/PRIVACY-POLICY.md`, `legal/TERMS-OF-USE.md`); `/privacy` also shows the section 13 notice. Rendering the markdown needs a renderer or a build step outside this work order's size, and `legal/` is not inside `apps/web`, so it would not deploy with it. A participant cannot open a repository file: a rendered copy is needed before real participants (suggest R2c).
3. "No thanks" is Sign out (POST `/auth/sign-out`), with a plain explanation; the notice is shown again at the next sign-in.
4. Country: the select lists the countries from `app.supported_countries()` and "My country is not listed", which asks for a two-letter code (the database checks `^[A-Z]{2}$`). Without that option nobody could ever give an unsupported country, which FR-9 needs. A note says the pilot is not open there. An unsupported answer is kept by the database and the person is held at not-available.
5. Pre-fills (FR-6): hemisphere from a short list of mostly-southern countries (everything else north), currency INR for India else USD (the `profiles.currency` default). Both can be changed. The currency list is `Intl.supportedValuesOf('currency')`, built on the server.

## Document gaps (quoted)

The work order says the versions come from `app.public_setting`; that is what is built (decision 1). The migration comment ("the web build's constants must equal them") is moot.
- FDD FR-4: "Tapping "No thanks" or closing the pop-up does not join the pilot. The user then sees only a page offering Export my data, Leave the pilot (the deletion in FR-66) and Sign out". LLD 9.1: "`/not-available` offers only Export my data, Leave the pilot and Sign out." The work order: "no Decline path except sign out". Built: Sign out only. Export and Leave the pilot are R2c.
- The notice text itself (Privacy Policy section 13, FR-3) tells people "You can leave at any time with Leave the pilot, which deletes your account and data". That control does not exist until R2c. Until then the notice promises something the app cannot do; the pilot must not open to real participants before R2c.
- FR-61 describes the locked sharing setting in Settings with an information tooltip. Settings is R2c; the locked, ticked, disabled control and the FR-61 sentence (in a native details element, which works without scripts) are on the pilot notice page as the work order asks.
- FR-7 (start from popular items or add my own) is not built: there is no catalogue picker yet. After onboarding the person lands on the wardrobe.
- FR-3 calls the notice a "pop-up"; LLD 9.1 calls it "the blocking pop-up page". Built as a full page.
- FR-6 says hemisphere is "pre-filled from the country"; no document gives the mapping (decision 5).

CC5 screenshots (WO-0052); the screens were walked once by hand in the built app against the local stack (sign-up, confirmation, accept-terms, pilot-notice, onboarding for India and for an unlisted country) and the test users were deleted.


# R2b WO-0052 notes: Supabase repository, backend switch and demo evidence

## Built (all under apps/web)
- `lib/supabase/repository.ts` `SupabaseRepository` (items, outfits, wishlist entries, `feedback`) over PostgREST with the signed-in person's own session and the publishable key. `lib/supabase/mapping.ts` is the pure mapping both ways. `lib/supabase/errors.ts` holds `RepositoryError` (fixed sentence per kind: network, session, refused, rejected, unsupported, unexpected) and `attempt()`, which the screens wrap around every change. `lib/supabase/backend.ts` chooses the repository. `lib/repository.ts` gains an optional `feedback` sink on `WardrobeRepository`.
- Screens: `useRepository` now calls `chooseRepository()`. `ItemForm`, `WardrobeList` and `OutfitsView` show a failed load or change in a `role="alert"` paragraph, keep the form and the card as they were, and never replace a list that could not be loaded by an empty one. Accept and Reject call `repo.feedback?.record(event)` after the local event log has recorded it.
- Tests: `mapping.test.ts` (round trip property, 500 random items, outfits, wishlist entries; feedback rows), `repository.test.ts` (fake client: requests, every failure kind, no-session, rollback, `attempt`, backend switch), `repository.int.test.ts` (12 tests against the real stack), the updated strict no-network and import tests (`components/outfits/outfits.test.ts`, `lib/supabase/source.test.ts`).

## Decisions
1. Backend switch. `pickBackend(backend, state)`: `local` whenever the app is not set to `supabase`; `supabase` only when it is set to `supabase` AND the gate state is `ready`; otherwise `blocked`, a repository whose every call fails with the session (or network) sentence. The work order says "otherwise local". For a person who is signed in to an account that would keep their wardrobe on this device only without saying so, so `blocked` is used when the app is set to `supabase`. In normal use the proxy never lets a not-ready person reach a consumer page, so `blocked` is the race case (session ended after the page loaded).
2. Colour. A written item row never carries `colour_hex`, `colour_family`, `is_multicolour` or the second colour; the trigger sets them. Reads take them back from the database. The int suite inserts 150 random items and checks that the database's family equals the TypeScript `colourFamily` for each.
3. Items: `origin` is always `manual` (the demo loader too). `archive` and `restore` are one update each and set `archived_at` from the client clock. `remove` is refused with "Deleting an item is not available yet. Archive it instead": the migration grants no delete on items (see gap 3).
4. Outfits: the outfit row (`name` "<occasion> outfit", `occasions` = [occasion]), then its pieces; if the pieces fail the outfit is deleted again (best effort) and the error is thrown. `update` upserts new or moved pieces first and deletes the dropped ones last. A piece that fills two slots (Suit) is one row (`outfit_items` is keyed on outfit and item) under its first slot and is put back in every slot it fills when read, using the item's sub-type from the slot map. An outfit with no occasion the app knows is skipped on read.
5. The engine's `score` and `reasons` have no column. They are kept, lossless, in `outfits.notes` as `{"v":1,"score":..,"reasons":[..]}`; notes written by anyone else read as no score and no reasons (gap 4).
6. Wishlist: colour family is stored as the reference swatch RGB of the family (the trigger gives the same family back; checked by test), `Multi` as the `is_multicolour` flag with no RGB. `origin` is stored (`unlock` for Wardrobe unlock). `addUnlockToWishlist` is unchanged and writes through the repository.
7. Feedback: a row has exactly `occasion`, `rule_ids` (filtered to the database's rule-id pattern), `accepted`, `engine_config` and the owner. It is built from four named fields, so no item id or name can ride along. A failure never blocks Accept or Reject; the note says the answer could not be sent.
8. No-network test, still strict. The repository modules (`repository.ts`, `mapping.ts`, `errors.ts`) are scanned with the same rules as every other lib file (no fetch, XHR, socket or URL): they reach the service only through a client handed to them. Exactly one module besides the sign-in modules is left out of that scan by name: `lib/supabase/backend.ts`, which creates the session client and reads the sign-in state to choose the repository. `source.test.ts` pins its imports, requires that only `components/use-repository.ts` imports it, and requires that the suggestion path imports nothing from `lib/supabase` except `config`, `errors`, `backend`, `repository` and `mapping`. The Supabase package is imported once, as a type only. The two learned-file fetches in `engine-config.ts` are unchanged.
9. Wording: `layout.tsx` description no longer says "Everything stays in this browser". The Outfits page says what is stored when the backend is `supabase`.

## Document gaps (quoted)
1. The work order: "suggestion accept/reject also insert `app.suggestion_feedback` rows (rule_ids from the engine, engine_config string, occasion, season; NO item ids or names)". The table (migration core_tables) has `occasion`, `rule_ids`, `accepted`, `engine_config`, `created_at` and no season; LLD 4.4 lists "`occasion`, `rule_ids[]`, `accepted`, `engine_config`". Season is not stored (it stays in the local event log). A column needs a migration, which this release may not make.
2. The work order: "`useRepository` picks it when `NEXT_PUBLIC_DATA_BACKEND=supabase` and the user is ready, else the local one". Built differently when the app is set to `supabase` and the person is not ready (decision 1).
3. The migration: "No delete on items (LLD 4.6: the delete route removes storage objects first)". The wardrobe screen has a "Delete item" button that calls `items.remove`; against Supabase it shows the refusal sentence. The delete route is not built (R2c).
4. LLD 4.4 lists outfits as "`name`, `occasions[]`, `seasons[]`, `notes`, `needs_attention`": nothing for a score or reasons, which `SavedOutfit` carries. They are in `notes` (decision 5). If the product wants user notes on outfits later, the score and reasons need their own columns first.
5. `UnlockPanel` still says "Worked out in this browser; nothing is sent anywhere". True of working out the list; adding an entry to the wishlist now stores it in the account. Wording not changed (not asked for).
6. The sign-in redirect keeps `?next=%2Foutfits` in the URL but after sign-in the browser landed on `/`, not `/outfits` (seen in the evidence run). Not investigated in WO-0052. Fixed in WO-0053 (item m1, below).

## Not done

- No unit test renders the three screens' error paths (the repo has no DOM test library and none may be added); the item-form network failure was exercised once in the real browser (see TRANSCRIPT.md); the accept, archive and load failures are covered at the repository and `attempt()` level only.
- Counted lines were over 500 (see the WO-0052 report). The maker made no commits itself; the work was committed afterwards by the orchestrator as a212fde.


# R2b WO-0053 notes: fix loop 1 (open redirect, strict no-network scan, proxy tests)

## Built (all under apps/web, plus these notes)
1. B1, open redirect. `safeNextPath` (lib/auth-form.ts) now refuses any input with a backslash or a control character, and returns the home page unless the parsed path stays on the placeholder origin and does not start with `//` (the reviewer's `/.//host` and `/%2e//host` forms parse to `//host`). 25 payloads in test-support/redirect-payloads.ts, a 4000-case generated check, and legitimate paths with query strings kept. Both sinks are tested: the callback route's Location header (app/auth/routes.test.ts calls `GET` with a fake session) and the sign-in form's target (`finishSignIn`, plus a source test of AuthForm). lib/supabase/source.test.ts now lists every place the app leaves a page or redirects (seeOther, location.assign, router.push/replace, NextResponse.redirect); a new sink fails that list.
2. m1. After sign-in the form calls `finishSignIn(next, (to) => window.location.assign(to))`: a full navigation, no `router.replace` plus `router.refresh` race. Browser check below.
3. M1, strict no-network scan. test-support/network-scan.ts holds the rule and the only allowances (the two `engine-config.ts` fetches, and the placeholder host literal `http://sparta.invalid` once each in `lib/auth-form.ts` and `lib/supabase/gate.ts`, which now has a single literal). The rule runs on every non-test file of lib, components and app plus proxy.ts and next.config.ts, including backend, gate-state, browser, server, proxy-session, auth-actions and consent-actions (the earlier list of exclusions applied to the IMPORT rule only and still does). A test compares the scanned list with the files on disk, and appends a request to each of backend, gate-state, browser, repository and mapping (and to every scanned file) and expects the scan to fail.
4. M2. `proxy.test.ts`: the `proxy()` wrapper with a stubbed session updater that throws (503, fixed text, no detail), the matcher against consumer routes, near misses and the public files. The matcher was tightened so that only exact names and the two `/_next` prefixes are excluded (`/icon.svgx` and `/_next/staticx` used to skip the check).
5. m2. consent.int.test.ts bumps `current_notice_version`, `current_terms_version` and `current_privacy_version` in `ops.settings` one at a time and expects `needs_pilot_notice` / `needs_documents`, then restores the value in a `finally`. Because the versions are global, the integration suites could disturb one another when vitest runs them together (seen: three repository tests failed once). Each integration suite now takes `lockStack()` (test-support/stack.ts, a lock directory) from its first hook to its last, so they run one after the other.
6. m3. `needsNoSession(method, path)` (lib/supabase/gate.ts): the public pages (`/about`, `/privacy`, `/terms`, `/notice`, `/maintenance`) and POST `/auth/sign-out` are decided in `proxy()` before the session updater is called; everything else, including `/auth/callback`, still fails closed. The sign-out route also removes the device's `sb-` cookies itself, because a sign-out call that cannot reach the account service leaves them in place.
7. m4. The gate puts the path and its query string into `next`, encoded as one parameter (`/outfits?anchor=item-1` becomes `/sign-in?next=%2Foutfits%3Fanchor%3Ditem-1`); the proxy hands the gate path plus query.
8. m5. `signUpWithEmail` maps GoTrue's `user_already_exists` (HTTP 422, which the local stack does return for a confirmed or an unconfirmed address) to the same success as a new sign-up, so the screen shows "Check your email". Limit: the Auth API itself still answers 422 `user_already_exists` to anyone who calls it directly, so this removes the difference from the screen only.
9. m8. The `signOut` action is now the one the sign-out route uses. The item form offers "Delete item" only when the backend is not `supabase` (`canDeleteItems()`); delete is refused by design against the database (LLD 4.6).
10. M3 (partial). next.config.ts sends on every route: `Content-Security-Policy: frame-ancestors 'none'; form-action 'self'; base-uri 'self'; object-src 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`. This CSP is PARTIAL on purpose: it has no `script-src`, `style-src`, `connect-src` or `default-src`. A full policy with a per-request script nonce (and the matching changes for Next's inline scripts and the Supabase connect-src) is LATER work and is not part of this release. Checked on the built app with `curl -I` (TRANSCRIPT.md) and in the browser (sign-in, sign-out form post, items, outfits all worked; no CSP message in the console).
11. Stale evidence: the WO-0052 line that said nothing had been committed, and the transcript's claim about what screenshot 10 shows, are corrected.
