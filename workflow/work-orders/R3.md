# Release R3: Suggestions (spec and work orders)
Date: 2026-11-04
Requested by: product owner delegation of 2026-11-04. Workflow v0.4; conventions in R0.md. DEVIATION LOGGED: the build environment has no Docker or Supabase CLI, so R2's database and auth cannot be run or verified here. The app therefore gets its data through a repository interface with a browser-local implementation (localStorage) for development and the demo; the Supabase implementation is R2 and is NOT built or claimed. R3 is built before R2 for that reason.

## Goal
A person can open the app, build a menswear wardrobe by hand, pick an occasion and get up to three explained outfits from the engine, accept, swap or reject them, with nothing leaving the browser.

## Completion conditions
- CC1: `bash workflow/gates/gate.sh` exits 0.
- CC2: `npm run build -w apps/web` exits 0 (Next.js production build, no type errors).
- CC3: `npm test` includes at least 25 tests for the app's non-UI logic: the `WardrobeRepository` interface and its localStorage implementation (create, update, archive, list, persistence across reload using a fake Storage), the item form's validation and automatic naming (colour family plus sub-type, FDD 13), colour family derivation on save via @sparta/taxonomy, the suggestion view-model (accept saves an outfit; reject discards; swap replaces one slot and re-validates), the local usage-event log (`suggestion_accepted`, `suggestion_rejected`, `suggestion_swapped`, `item_added` with `engine_config`), and the thin-wardrobe message (FR-54).
- CC4: a test proves no network request is made during suggest/swap (the app code calls no fetch/XHR in the suggestion path: a source grep test over apps/web/components/outfits and apps/web/lib).
- CC5: demo evidence: `workflow/evidence/R3/` holds screenshots and a short script of the built app running (dev server via the built-in browser): add 6 items, ask for Casual and Work, see three outfits with reasons, swap an item, accept one, see a thin wardrobe message with an almost-empty wardrobe, reload and see the data persist.
- CC6: accessibility basics checked by test or audit: every interactive control has an accessible name; the colour contrast of text meets 4.5:1 (state how it was checked); keyboard can complete the occasion pick and accept (FDD NFR).

## Scope fence
Will NOT touch: packages/taxonomy, packages/rules (read-only), supabase/*, services/*, docs/*, legal/*. Will NOT do: auth, Supabase, photo, receipts, vendor side, Complete the look and Wardrobe unlock (R4).

## Dependencies approved by delegation
next, react, react-dom, @types/react, @types/react-dom, and @types/node (pin exact current stable versions; Next.js 16 if available else the latest 15.x; explain the choice in the report). No CSS framework: plain CSS modules or one global stylesheet with CSS variables and a dark mode via prefers-color-scheme.

## Risk routing
Sensitive paths: none (no auth, no DB). Route: execute.
