# Release R2b: App sign-in, consent screens and Supabase repository (spec and work orders)
Date: 2026-11-05
Requested by: product owner delegation (build until the MVP is done). Workflow v0.4; conventions in R0.md. Branch release/R2b (from main, which has R0 to R5a and R2a). The local Supabase stack runs (Docker via Colima). Dependencies approved by delegation: @supabase/supabase-js and @supabase/ssr (exact pins). Keys: the app reads NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY from apps/web/.env.local (git-ignored; commit only apps/web/.env.example with empty values); integration tests read the local stack's values at run time from `supabase status -o json` and never write them to a file. Never use or expose the service-role/secret key in the app.

## Goal
A person invited by email can sign up, confirm the email, sign in, accept the Terms, Privacy Policy and pilot notice, finish onboarding (country, hemisphere), and then use the wardrobe and outfits screens with their data stored in Supabase under row-level security; the browser-local repository stays available as the offline/demo backend.

## Completion conditions
- CC1: `bash workflow/gates/gate.sh` exits 0 (db_tests runs for real).
- CC2: `npm run build -w apps/web` exits 0.
- CC3: a vitest integration suite `apps/web/lib/supabase/*.int.test.ts` (skips with a clear message when the stack is not running) proves against the REAL stack: uninvited sign-up refused (the FR-8 message), invited sign-up then email confirmation through Mailpit then sign-in; before acceptance a signed-in user gets no wardrobe rows and the app routes to accept-terms; after `accept_documents`, consent record and `complete_onboarding` the same user can create, read, update and archive items through the SupabaseRepository; a second user cannot see or change the first user's rows through the repository; an unsupported country gives the not-available state; sign-out clears the session.
- CC4: route gating (`apps/web/proxy.ts`, Next 16 name for middleware) per LLD 9.1: unauthenticated users go to sign-in for the consumer routes; signed-in users without acceptance/consent/onboarding go to the right step; unit tests of the pure gating function (at least 20 cases) and a source test that the service-role key and the string 'service_role' appear nowhere in apps/web.
- CC5: evidence in workflow/evidence/R2b/ with REAL screenshots (built-in browser) and an honest transcript: sign-up refusal for an uninvited address, invited sign-up, Mailpit confirmation, sign-in, the three consent screens, onboarding, adding an item, getting outfits, sign-out; state exactly what was scripted versus clicked.
- CC6: accessibility basics for every new screen (labelled inputs, errors announced, focus order, 4.5:1 contrast) with tests in the style of apps/web/components/wardrobe/a11y.test.ts; passwords: minimum 10 characters stated in the UI and validated client side too.
- CC7 (G4): no H&M-derived file or data; learned parts still default off; no key in any committed file (`secret_scan`).

## Scope fence
Will NOT touch: packages/*, supabase/migrations (database changes are R2a; if a migration is needed STOP and report), ml/*, docs/*, legal/*, anything H&M. Will NOT do: export, delete account, Leave the pilot, About page (R2c), vendor side, photos, receipts.

## Risk routing
Sensitive: authentication and session code. Delegated approval; an Opus security reviewer checks every route and cookie handling.
