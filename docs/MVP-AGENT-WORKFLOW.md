## 1. What this is and the one rule behind it

A set of agents with fixed jobs builds the MVP in **small releases**. Every release goes through the same loop: plan, consult, design, build, check, demo, approve, retro. The loop rests on one rule, **maker and checker are never the same agent**: whoever writes something never judges it, and a checker may only fail work by pointing to a script result or a quoted line of the specification.

The product owner stays the only authority on scope. Agents propose; the owner, the style specialist (Arpan Shah) and the solution architect (C. Prashanth) decide what the documents already say they decide (BRD section 5, which states who owns scope, the taxonomy, rules and weights, and the HLD and LLD; the delegation of technology choices to the SA is in BRD section 8; FDD FOI-8 to FOI-12; HLD HOI-5).

## 4. The release loop

```
Plan ─► Consult ─► Design ─► Build ─► Check ─► Demo ─► Approve ─► Retro ─┐
  ▲                           ▲ │        │                               │
  │                           └─┴─ fix (at most 2 loops) ◄─ defects      │
  └──────────────── improvements and the next release ◄──────────────────┘
```

1. **Plan.** The orchestrator reads `workflow/STATE.md`, the BRD, FDD and LLD sections for the release, and the last retro. The spec agent writes work orders (section 5). Spec QC checks each against the definition of ready (G1); the product owner approves the scope.
2. **Consult.** Only where a work order names a consultant (the style consultant for changes to outfit rules R1 to R8 (LLD 9.5); the legal consultant for anything touching data sources). Memos are short, cite the document, and recommend; the orchestrator decides.
3. **Design** (user-facing work orders only). The UX agent writes the brief; the visual craft agent builds the components and tokens against it; the frontend maker builds the pages; the critic scores. A score below the bar returns the work to the visual agent.
4. **Build.** One maker per work order, in an isolated worktree on its own branch. Work orders that touch different files can run in parallel; two makers never edit the same files, and no file has two owners (section 3 splits the design files from the pages).
5. **Check.** Gate scripts first; if red, back to the maker (no judgement is spent on failing work). Then Spec QC against the spec on the base branch, the review gate (code review, security review, and model QC where a model changed; G2b), and the privacy and licence gate. At most **two** fix loops per work order; a third failure goes to the orchestrator, who splits it, re-plans or escalates to the owner.
6. **Demo.** Once green, the demo agent shows the release running: in the app from R2, and as a recorded test run for R0 and R1.
7. **Approve.** The release approver reads the evidence. The product owner's final yes is already given for the MVP build (section 11a): the orchestrator merges into the local `main` and tags; pushing stays human.
8. **Retro.** Section 8. Improvements to the workflow wait for the workflow approver's yes before they apply.

### 4.1 Preconditions before R0 (the product owner's yes; an agent cannot tick these)

The owner ticks each line in `workflow/STATE.md` (section 9 format) with the date. Until every line is ticked, the orchestrator starts no work order.

- [ ] **Local commits are agreed.** Agents may commit on branches in this repository. Push, merge to `main` and tags still need a yes each time (section 10, rule 3).
- [ ] **The specification is committed and merged into `main` by the owner.** BRD, FDD, HLD, LLD, this workflow document, `legal/` and `workflow/` are committed and merged into `main` by the owner, because `release/R0` is cut from `main`; the v1.4 documents exist only, uncommitted, on the branch `engine-hm-images`. Worktrees and Spec QC's "spec on the base branch" cannot see uncommitted files.
- [ ] **The branch model is accepted.** Each release has one **integration branch** `release/R<n>`, cut from `main` (R1 onward: from `main` after R0 is merged). Each work order runs on its own branch `wo/WO-nnnn` in its own worktree, cut from the integration branch. The orchestrator merges a work-order branch into the integration branch only after G2, G2b, G3 and G4 are green. The integration branch is **Spec QC's base branch** (section 3, Spec QC). The merge of `release/R<n>` into `main` is the owner's, at G6. Until G7 is closed, `models.manifest.json` on `main`, on every `release/R<n>` branch and on every `wo/` branch marks the three H&M-trained files as not yet built; G4 runs again on the release -> `main` diff before G6.
- [ ] **The permission mode for unattended runs is approved** (section 9, step 4).

## 5. Work orders, ready and done

A work order is one file, `workflow/work-orders/WO-nnnn.md`:

| Field | Content |
| --- | --- |
| Goal | One sentence, user-visible if it can be |
| Traces to | Requirement IDs (BR, FR, LD, HD) and the document sections that define the behaviour |
| Setup | Absolute paths come from `workflow/local.env` (copy `workflow/local.env.example`; the real file is git-ignored): `SPARTA_DATA_ROOT_HM` and `SPARTA_DATA_ROOT_MNIST` (the datasets), `SPARTA_TEAM_PHOTOS` (team photos for R5 and Model QC, kept outside the repository, LLD 7.7), `SPARTA_HM_CACHE` (the one folder for H&M derived caches, LLD 13.4) and `SPARTA_ARTIFACT_DIR` (trained files for Model QC on a fresh checkout). Agents in a worktree or on a fresh checkout read these settings and never a relative path; the `data/recommendation-engine/hm` symlink is a convenience only |
| In scope, out of scope | Files or areas the maker may touch, and the ones it may not |
| Acceptance checks | Commands or observable steps, each with an expected result and, where a number matters, its threshold; at least one is a script |
| Consultants | Which memos must exist before the build starts |
| Time box | Wall-clock and cost limits (section 10) |
| Owner agent, checker agents | By role |

**Definition of ready:** the preconditions of section 4.1 are ticked, and the section 4.2 rows for this release; traces to a requirement that exists; every acceptance check is runnable; out-of-scope is explicit; the setup line names every path the work needs; consultants named where needed; no open question that would change the checks.

**Definition of done:** all acceptance checks pass on a clean checkout; gate scripts green; Spec QC cites the evidence for each check; the privacy and licence gate passes; documents are in step (doc-sync lists any change; a diff to the BRD, FDD or legal files is signed by the product owner, a diff to the HLD or LLD by the SA); `STATE.md` updated; no TODO left in code without an item in `STATE.md`.

## 9. Usage limits and resuming

Long builds will reach the five-hour usage limit, and weekly limits sit behind it. The workflow does not wait for a limit message, because a run that is cut off in the middle of a work order cannot react. It checks the position before and after every work order, arms the resume trigger **before** each work order, and stops with a clean checkpoint while there is still room to write one.

1. **Read the usage twice per work order.** Before and after every work order the orchestrator calls `mcp__ccd_session_mgmt__get_usage` and writes the five-hour and weekly positions into `workflow/STATE.md`. The orchestrator reads the usage and the reset time; the trigger never does. If the result says `unavailable` or `not_applicable` (no plan limits can be read), the orchestrator stops at once, sets `Status: waiting-for-owner` and says why: without a reading the pre-armed rule cannot work.
2. **Five-hour window 85% used or more.** The orchestrator writes the checkpoint and sets `Status: waiting-for-limit-reset`. The trigger is already armed (step 4); if `STATE.md` names no trigger for this window, arm it now as in step 4, then stop.
3. **Any weekly window 90% used or more.** The 90% rule applies to every weekly window the result lists, including the per-model ones (for example an Opus-only weekly window). The orchestrator sets `Status: waiting-for-owner`, writes the checkpoint, deletes the armed trigger (a five-hour reset does not help) and stops.
4. **Arm the trigger before each work order, not after.** After a usage check that passes and before it hands out a work order, the orchestrator makes sure one one-shot trigger exists for the current five-hour window: `mcp__scheduled-tasks__create_scheduled_task` with `fireAt` = the window's `resetsAt` plus two minutes, a **unique** id `sparta-resume-<yyyymmddhhmm>` (the fire time; the tool refuses an id that already exists) and the prompt of step 8. It writes the id and `fireAt` into `STATE.md` (`Resume trigger`). If `STATE.md` already names a trigger for the same `resetsAt`, it creates nothing. Arming first means a cut-off in the middle of a work order is covered; the lock (step 6) stops the trigger from starting a second orchestrator if the first is still alive. **At every start, delete stale triggers:** list the scheduled tasks and delete every `sparta-resume-*` whose time has passed or that `STATE.md` does not name; clear the field only if the trigger it named was deleted. If the tool refuses the id, list the tasks. If a live `sparta-resume-*` task already fires at this reset, record it; otherwise create the task with the free id the tool offers and record that. **Permission mode:** the tool only may save the task in the session's permission mode, and its result says whether it did. If it did not, the orchestrator deletes the task it just created, sets `Status: waiting-for-owner`, schedules nothing and stops before the work order; an unattended run must never need a prompt for work already authorised (the owner approves the mode, section 4.1). The scheduler fires only while the Claude app is open; if the app was closed it runs at the next launch.
5. **Where `STATE.md` lives.** In the primary checkout, `/Users/ambarish/Documents/Claude/Sparta/sparta/workflow/STATE.md`, never inside a subagent's worktree. Fields: `Updated` (IST), `Status` (`running`, `waiting-for-limit-reset`, `waiting-for-owner`, `idle`), `Resume trigger` (task id and `fireAt`, or none), `In-flight branches` (the work-order branches and worktrees that are not merged), the integration branch, the preconditions ticked (4.1, 4.2), what is done and next, and the usage position. It is committed only as the owner agrees (4.1).
6. **Lock and heartbeat.** A run that finds `Status: running` with `Updated` within the last 30 minutes exits at once, so two orchestrators never work at the same time. While it runs, `Updated` is refreshed at least every 15 minutes, also while the orchestrator waits for a subagent, so the lock does not lapse under a live run: a background shell job, started before each work order, rewrites `Updated` every 10 minutes and ends with the orchestrator session. Subagents run in the background. A `running` status whose `Updated` is older than 30 minutes means the run died, and the next run may take over.
7. **In-flight subagents.** They finish, or a subagent that cannot finish leaves its worktree in place and its branch name goes into `In-flight branches`.
8. **The resume prompt** (all paths absolute): *"Resume the Sparta MVP build. Read /Users/ambarish/Documents/Claude/Sparta/sparta/workflow/STATE.md and /Users/ambarish/Documents/Claude/Sparta/sparta/docs/MVP-AGENT-WORKFLOW.md. Stop at once and change nothing unless Status is `waiting-for-limit-reset`, or Status is `running` and Updated is more than 30 minutes old (the earlier run died). In particular, stop if Status is `waiting-for-owner` or `idle`, or `running` and fresh. Otherwise set Status to running and Updated to now, delete the stale resume triggers (section 9, step 4), call get_usage and apply section 9, run the gate scripts on the branches named in In-flight branches to confirm the state, then continue from the next step. Do not redo finished work orders."*
9. **What the resumed run may do.** It starts at the plan step with the checkpoint as its only memory. It only resumes work already authorised in this document. It never merges to `main`, pushes, changes a data-licence decision, creates an account or enters a key, or switches on a learned part in a pilot or production build. Anything not authorised is a stop with `Status: waiting-for-owner`, not a prompt nobody will answer.

## 10. Standing rules for every agent

These come from the product owner's instructions and from mistakes already made in this project.

1. **Stay in the project.** Work in `sparta/` and the paths a work order names; the only folders outside it are the five named in `workflow/local.env`: the two dataset folders, the team photos (`SPARTA_TEAM_PHOTOS`), the one H&M derived cache (`SPARTA_HM_CACHE`) and the artifact folder (`SPARTA_ARTIFACT_DIR`). Do not search the home directory or other folders; if something is not where it should be, ask.
2. **No Claude attribution lines** in commits or pull requests (`Co-Authored-By: Claude`, "Generated with Claude Code"). The product owner is the author.
3. **Outward and hard-to-reverse actions need a yes:** push to `main`, force-push, tagging a release, deleting data, sending anything off the machine. Approval for one action is not approval for the next.
4. **Time-box investigations.** An investigation or background job that is not on the critical path gets 10 minutes of wall-clock time. Beyond that the agent reports what it knows and asks. No brute-force searches (the seed hunt of 3 November 2026 took 17 minutes and changed nothing).
5. **Say what was verified.** Report what ran and what it showed, name what was not checked, and do not call something done that no check covers.
6. **No participant data in training, ever** (BR-28, BR-52). No H&M row, photograph or ID leaves its folder (the derived cache `SPARTA_HM_CACHE` is the one named exception, deleted per LLD 13.4), enters the database, storage, worker image or repository, or reaches a user (BR-59). H&M-trained files are not committed.
7. **The H&M-trained files are not pinned on `main`, and are in no pilot or production build, and the learned parts stay off in a pilot or production build,** until G7 (OI-5) is closed by the people it belongs to. Until then `models.manifest.json` on `main`, on every `release/R<n>` branch and on every `wo/` branch marks `garment-cnn-v2.onnx`, `pairing-prior-v1.json` and `unlock-candidates.json` as not yet built.
8. **Short reports.** Findings first, in plain words; detail only on request.
9. **No unrequested scope.** A better idea goes into the retro or to the owner, not into the diff.
10. **Agents never create accounts or enter keys, tokens or passwords** (section 4.2); a missing account stops the work with `waiting-for-owner`.
11. **Background work is owned, bounded and verified, or it does not run.** (Added on the product owner's instruction of 2026-11-05 after a wait loop with a wrong success text ran for about a day and stalled the build.)
    - Before starting anything in the background (a watcher, a dev server, a build, a subagent) the starter names what it is waiting for and sets a hard timeout (default 10 minutes; at most 30). A wait with no timeout is not allowed.
    - **Readiness is checked with the tool's own status command** (`supabase status`, `docker ps`, `curl` to the health URL, an exit code), never by searching for a text line in a log. A check must also cover the failure outcomes (error, crash, timeout), not only success.
    - If the awaited thing is already ready, or its check cannot match, the wait is cancelled at once; a wait that has produced no event after its timeout is cancelled and reported, not re-armed silently.
    - **Sweep.** After every work order, before every report to the owner and before stopping, run `bash workflow/gates/sweep.sh` (use `--kill` for strays). It lists dev servers, wait loops, log tails, long sleeps, listening web ports, running containers and scratch clones. Only the local database stack and the Colima VM may stay up, and only while database work is planned; stop them (`supabase stop`, `colima stop`) when the build pauses.
    - **Makers and checkers stop what they start**: a server or watcher started for a demo or a test is stopped before the report, and the report says so. An agent that leaves a server running has not finished the work order.
    - **Every subagent gets a time box in its brief** (default 45 minutes for a maker, 45 minutes for a verifier, 20 minutes for a re-check of a fix); the orchestrator checks elapsed time at each sweep and sends a wrap-up message to any agent past its box, asking it to report what it has and say what it skipped.
    - The orchestrator checks the agent list (`ListAgents`) and the scheduled tasks at each sweep and stops anything that has no work order behind it; a resume trigger that has fired or is no longer needed is deleted, not left disabled.
12. **Lint is law, baselines only shrink, and a merge needs a FULL gate.** (Added on the product owner's instruction of 2026-11-15 after the audit in `workflow/work-orders/Audit.md`.)
    - Every lint rule is an error. Rules live in `eslint.config.js` (TypeScript), `workflow/gates/repo_lint.py` (everything else), `supabase/tests/database/900_catalog_lint.test.sql` and `workflow/gates/db_lint.sh` (database). `docs/LINT-RULES.md` explains each.
    - No inline `eslint-disable`, no `@ts-ignore`, no skipped or focused test. An exception exists only as an entry in a baseline file (`eslint-suppressions.json`, `repo_lint.baseline.json`, `db_lint.baseline.json`) with a work order that removes it. A maker never adds an entry; the Gate engineer does, in a work order that says why.
    - A defect that a human or a checker finds and a rule could have caught gets its rule in the same fix (retro section 3, "Escapes").
    - **Before a merge into `main` or a release branch the orchestrator runs `GATE_STRICT=1 bash workflow/gates/gate.sh`** and the last line must be `GATE: PASS (FULL: no stage skipped a check)`. `PASS (PARTIAL)` is for a maker's quick loop only and is never evidence of done.

13. **Build by the guide.** (Added on the product owner's instruction of 2026-11-16, WO-0149.) Every maker and every checker reads `docs/BUILD-GUIDE.md` before a work order: it holds the steps for building one work order, the checks to run for each kind of change, the checker's method, and the mistakes this project has already made once with the habit that avoids each. The orchestrator names the guide in every brief. A new habit needs an incident behind it, and where a script can check it the rule is added in the same work order (`docs/LINT-RULES.md`).
