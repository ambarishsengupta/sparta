# Release R2c: Data rights and account pages (spec and work orders)
Date: 2026-11-05
Requested by: product owner delegation (build until the MVP is done; section 11a of the workflow). Conventions in R0.md. Branch release/R2c (from main with R0 to R5a, R2a, R2b). Local Supabase stack running (`supabase status`). Dependencies: none new.
Why now: the pilot notice promises "Leave the pilot" and the not-available page must offer Export and Leave (FR-4); the pilot cannot open to real participants without this release.

## Goal
A signed-in participant can export all their data, leave the pilot (which deletes the account and every row of theirs), see Settings and an About page, and read the Terms and Privacy Policy in the app; all verified against the real local stack.

## Completion conditions
- CC1: `bash workflow/gates/gate.sh` exits 0 (db_tests real).
- CC2: `supabase test db` passes with new pgTAP files: (a) `app.export_my_data()` returns one JSON document with every row the caller owns in every `app` table and nothing of any other user (isolation test across all tables, derived from the catalog so a new table without export coverage fails); (b) `app.delete_my_account()` deletes the caller's auth user and, through cascades, every row in every `app` table (a loop over all `app` tables proves zero rows remain for the caller and the other user's rows are unchanged), is idempotent, refuses anon and non-consumer roles, cannot delete another user, writes only counts (no personal data) to `ops.daily_counts`, and ends the caller's sessions; (c) both functions are `security definer` with empty search_path only if required (prefer security invoker for export), executable by `authenticated` only; (d) mutation proof of at least 12 mutants (a missing cascade, a weakened caller check, an export that leaks another user's row, a grant to anon).
- CC3: real-stack integration tests: export returns the caller's data and only theirs; delete after re-authentication removes the user (signing in again fails), all their rows are gone, the second user is unaffected; the not-available user can export and delete; a user who is not signed in or whose password is wrong cannot delete.
- CC4: pages: Settings (profile display name, country shown, hemisphere, currency, occasions editable where RLS allows; the sharing setting shown locked ON with the FR-61 tooltip; Export my data; Leave the pilot with a confirmation step that re-enters the password; sign-out), About (FR-67: who runs the pilot, the privacy contact address from a configuration value `NEXT_PUBLIC_CONTACT_EMAIL` (empty means the page says the address is not configured), hosting region from config, supported countries from `app.supported_countries`, the plan for the end of the pilot from legal/PRIVACY-POLICY.md section 7, links to Privacy, Terms and the pilot notice), `/privacy` and `/terms` rendering legal/PRIVACY-POLICY.md and legal/TERMS-OF-USE.md as HTML via a small SAFE renderer in the repo (no new dependency; escape every character first; support headings, paragraphs, lists, tables, emphasis, links to http(s) and relative only; tests with hostile markdown), the not-available page offering Export, Leave the pilot and Sign out (FR-4), a goodbye page after leaving. All reached through decideRoute states (not-available users may reach export/leave/about).
- CC5: evidence in workflow/evidence/R2c/ with real screenshots and an honest transcript (what was scripted vs clicked; stop servers when finished: rule 11).
- CC6: accessibility tests for the new pages; the no-network scan stays strict (the export is a download of data fetched through the Supabase repository modules or RPC, no other host); proxy and gate tests extended; no service-role key anywhere in apps/web; secret scan passes.
- CC7 (G4): nothing H&M-derived; learned parts off.

## Scope fence
Will NOT touch: packages/*, ml/*, services/*, docs/* except none, legal/* (read-only source for the pages), the learned parts. Will NOT do: vendor side, photos, receipts.
