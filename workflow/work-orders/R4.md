## Facts from WO-0010 that WO-0011 and WO-0012 rely on (committed on main)
- The prior built from the H&M data (local, git-ignored, in the artifact folder, AUC 0.608 with interval 0.601 to 0.615; it ships narrowly, so the learned layer stays OFF by default) has this format: `{ "version": 1, "min_pairs": 30, "type_pairs": { "<slot pair>": { "<first sub-type>": { "<second sub-type>": x } } }, "colour_pairs": { "<slot pair>": { "<first colour family>": { "<second colour family>": x } } } }`. Slot pairs: `Top+Bottom`, `Top+Footwear`, `Bottom+Footwear`, `Layer+Top`; the first slot supplies the first item. Each x is `sigmoid(clip(ln lift, -2, 2))` between 0.119 and 0.881; a missing entry is neutral (0.5). The pair score of two items is `sigmoid(logit(type x) + logit(colour x))`. An outfit's `pairing` is the mean over its available slot pairs. `unlock-candidates.json` is a bare array of `{sub_type, colour_family}` (at most 40).
- The engine currently uses `weights_base` (no pairing part). With a valid prior passed in, use `weights_with_pairing` and add the `pairing` part; with no prior (default), behaviour must be byte-identical to R1 (same ids, order, scores).
- `engine_config` string format: `gm1;emb0;pair0;ul:fb;w:base` (pair1 and w:pairing when the prior is on; ul:hm when the H&M unlock list is used).
