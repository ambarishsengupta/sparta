# Release R2a: Database foundations (spec and work orders)
Date: 2026-11-05
Requested by: product owner delegation of 2026-11-04 (build until the MVP is done, no approvals). Workflow v0.4; conventions in R0.md. Branch release/R2. Environment now has Docker (Colima) and the Supabase CLI 3.0.0 with the local stack running (`supabase status`: db 54322, api 54321, Studio 54323, Mailpit 54324). Local keys are the public Supabase demo defaults and are not secrets, but never copy any key into a committed file.
Scope note: R2a is the database only (consumer side): schemas, lookups, colour function, core `app` tables, row-level security, invitations/acceptances/consent, pgTAP tests. R2b (app sign-in, Supabase repository, notice and onboarding screens) and R2c (export, delete, Leave the pilot, About page) follow. Vendor tables, aggregation, storage buckets, jobs and the worker are R5 to R7.
Sensitive paths (agentic-os never-list 3): migrations, RLS and auth are touched. The owner delegated approvals; an Opus checker reviews every policy.

## Goal
`supabase db reset` builds the consumer database from migrations, and a pgTAP suite proves that one user can never read or change another user's data, that users without the pilot consent and the current documents get no rows, and that the colour function agrees with the TypeScript one.

## Completion conditions
- CC1: `bash workflow/gates/gate.sh` exits 0 (including a new stage `db_tests` that runs CC2 to CC4 when `supabase status` shows the stack running, and prints SKIPPED otherwise).
- CC2: `supabase db reset` exits 0 from the committed migrations and seed alone.
- CC3: `supabase test db` (pgTAP) exits 0. It includes: RLS isolation for EVERY table in the `app` schema (user A cannot select, insert for B, update or delete B's rows; an anonymous caller gets nothing); the consent gate (a signed-in user without the pilot-notice consent and the current Terms and Privacy acceptance gets no rows from the data tables, LLD 4.5); a consumer cannot change their own `role`, `age_confirmed` or `deleting`; the invitation check (LLD 4.9: `ops.check_invitation` returns the FR-8 error for an email not invited); `app.complete_onboarding` refuses a country not on the supported list; triggers: archiving an item flags outfits; an `item_features` row for another user's item is refused and an embedding whose length does not match its model version (32 or 64) is refused; colour: golden vectors for `catalog.colour_family` (`#00008B` Navy, `#1560BD` Blue, `#C0C0C0` Grey, `#36454F` Grey, `#800020` Maroon, null RGB gives null) and the `colour_hex` and `colour_family` fields are overwritten by the trigger whatever the client sends.
- CC4: a vitest integration test (skipped with a clear message when the stack is not running) compares `catalog.colour_family` in the database with `colourFamily` in @sparta/taxonomy on a deterministic grid of at least 5,000 RGB points (every family equal), and checks that every lookup row seeded in the database equals the taxonomy JSON (codes, sort, categories of sub-types).
- CC5: the seed is generated, not hand-typed: `supabase/scripts/gen-seed.ts` (run with tsx) writes `supabase/seed/lookups.sql` from packages/taxonomy; a test fails if the committed file differs from a fresh generation.
- CC6: `supabase db lint` reports no errors; no secret in any file; `models.manifest.json` untouched.

## Scope fence
Will NOT touch: apps/*, packages/* (read-only), ml/*, docs/*, legal/*, services/*, jobs/*. Will NOT do: vendor/catalog tables, analytics, storage buckets and policies, worker role, FX, collector.

## Glossary
- "consent gate" means LLD 4.5: data tables return no rows unless the profile has accepted the pilot notice and the current Terms and Privacy Policy versions.
