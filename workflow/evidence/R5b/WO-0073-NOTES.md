# WO-0073 notes (R5b): add-by-photo flow in the app

## What was built (apps/web)
- `lib/image-prep.ts`: `prepareImage(file, env)`: refuses non-images and sources over 30 MB, decodes with the picture's own orientation, draws on a canvas at most 1,200 px on the long side (never enlarges), encodes WebP (0.85, 0.7, 0.55), falls back to JPEG when the browser answers with another type, tries a second, smaller size only when no quality fits, result at most 4.5 MB (bucket limit 5 MB); at most 12 encodes; fixed human sentences (`PrepareError`). The browser parts (`createImageBitmap`, canvas, `toBlob`) are in `components/wardrobe/photo-backend.ts` (`browserEnv`) because `lib/` is type-checked without the DOM library. Canvas re-encoding drops EXIF and GPS.
- `lib/photo-flow.ts`: no browser, no network. `addByPhoto(file, deps, {signal, onStage, pollMs, timeoutMs})`: prepare, upload, create job, poll every 2 s with a hard timeout of 120 s (the last sleep never passes the deadline), 3 failed reads in a row end the wait, an abort ends it at once; never throws, every failure is an outcome with a fixed sentence (the job's `last_error` is never shown). `parsePhotoResult` validates the worker's result (all paths are `<own user id>/<plain file name>`, garment only for `garment-cnn-v1` with exactly 32 finite numbers, class 0 to 9, p 0 to 1; category and sub-type only as a real taxonomy pair). `prefillFrom`: NO category or sub-type unless the result carries a pair; dominant colour when present. `attachmentOf(result, 'cutout' | 'original')`. `abortableSleep` clears its timer on abort.
- `components/wardrobe/photo-backend.ts`: the Supabase side with the person's own session and the publishable key only: upload to the private `item-images` bucket at `<uid>/<32 hex>-original.<webp|jpg>` (no upsert), insert into `app.jobs` exactly `(user_id, type 'photo', input {path})`, read the job (`status,result`), 10-minute signed preview links. No other storage call (a test forbids remove, list, download, update, move, copy).
- `components/wardrobe/PhotoItemFlow.tsx` at `/items/new/photo`: choose a photo (labelled file input), progress text in a status region, failure sentence in an alert (with a link to add the item without a photo), preview of cut-out and original as a radio group in a labelled fieldset (alt texts), then `ItemForm` pre-filled. Leaving the page aborts the controller (cleanup of the effect), which clears the poll timer. Without `NEXT_PUBLIC_DATA_BACKEND=supabase` the page says it needs the account and offers the manual form. `WardrobeList` shows "Add by photo" only with the account backend.
- `ItemForm` gained an optional `photoStart`: the values the photo filled in, which of them are suggestions, and the attachment. "Suggested from your photo" is shown for category and sub-type only when a pair was suggested AND the values are still the suggested ones (once the person changes one, the label goes), and for the colour while it is still the suggested colour. The manual path (`createItemLogged(repo!, new EventLog(), result.input, 'manual')`) is textually unchanged; a pinned assertion in `events.test.ts` still holds.
- Repository: `ItemInput` gained optional `photo` (`PhotoAttachment`: image path, thumbnail path, optional features). `itemRow` writes origin `photo` and `image_path`/`image_thumb_path` for such an item (manual items: identical rows). `SupabaseRepository.items.create` writes the `app.item_features` row (model_version, garment_class, garment_p, 32-number embedding, owner) only when the attachment has features AND `featuresRow` finds them valid for the table's checks. A failure there does not fail or undo the save (PostgREST has no transaction here, and the client cannot delete items): the item exists without its shape numbers.

## GARMENT_GUESS_ENABLED
Default false in the worker: the result carries `garment: null`, so `prefillFrom` leaves category and sub-type empty, nothing is labelled as a garment suggestion, and no `item_features` row is written (unit tests and the real-stack test "garment null"). Only the colour is offered, labelled. No H&M-trained part is used or enabled; `models.manifest.json` untouched.

## Image cleanup on item delete: documented, not built
- A signed-in user has NO delete right on `items` (LLD 4.6; `canDeleteItems()` is false with the account backend and `SupabaseRepository.items.remove` is "unsupported") and NO delete or update policy on `storage.objects` (a real-stack test shows a user's `remove` leaves the file). So deleting an item's images from the app is not possible by policy.
- Consequence: the picture chosen for an item, the unchosen one, the thumbnails and the uploaded original stay in the private bucket until the person leaves the pilot (the Leave flow purges every object, WO-0071). Archiving keeps pictures. The LLD's `/api/items/images/cleanup` route (secret-key, server side) would remove the unchosen files and those of deleted items; it is not in this work order and not built. A user stores at most about 8 MB (policy), so the leftover is bounded.

## Deviations and gaps (honest)
1. **No real-browser evidence run and no screenshots.** I ran out of the 45-minute time box before building the app and driving it in the built-in browser. CC5's "real-browser evidence run" is therefore NOT done by this work order; the browser code (`browserEnv`, the page, the file input) is covered by unit tests over fakes and static renders only, never executed in a real browser. To do in a follow-up: build with `NEXT_PUBLIC_DATA_BACKEND=supabase`, upload a synthetic image, worker running in Docker.
2. LLD 9.4 says `prepareImage` re-encodes as JPEG at quality 0.85; the work order says WebP. Followed the work order (WebP, JPEG only as the fallback). The bucket allows both.
3. The analytics events `garment_guess_shown`, `garment_guess_kept`, `garment_guess_changed` (LLD 9.4) are NOT recorded: the event log has fixed event types and the server-side recorder is a later release. Only `item_added` with origin `photo` is logged locally.
4. Polling only (every 2 s, 120 s cap), no Realtime subscription (LLD 7.2 mentions Realtime with a 5 s fallback poll).
5. The `item_features` write is best effort (see above); a failure is silent. Features only order swap choices.
6. The preview uses the 320 px thumbnails, not the full cut-out; the wardrobe list does not show item pictures yet (no screen reads `image_path`; `ITEM_SELECT` unchanged).
7. Local (browser-only) mode: the photo page is closed (needs the account); nothing is stored in the browser for photos.
8. A job whose upload succeeded but whose job insert failed (or that timed out) leaves the uploaded original in storage (no delete right). Same bounded leftover.
9. No new dependencies. No new migration. Nothing outside `apps/web/**` and `workflow/evidence/R5b/**` touched (the Write tool was refused by a worktree hook for this path, so this file was written with a shell heredoc as instructed).
