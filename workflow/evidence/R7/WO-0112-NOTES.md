## Decisions and deviations (flag for the checker)
1. **First render is exactly 6 calls** (coverage, filter_options, one mix, purchase trend, wishlist trend, one spectrum). To stay at 6 the spectrum shows ONE category at a time (a select over the taxonomy categories, default the first), not every category at once; a hidden category shows the suppressed cell.
2. **A filter shows hidden segments from the unfiltered answer.** The component keeps the unfiltered answer of each view in a ref (this page only, never across users). A segment seen without the filter and missing with it is a row of "Not enough users to display". If a filter is set on a view never loaded without it, that view makes one extra unfiltered call (then none). After a first render a filter costs one call per view (1 mix + 2 trends), a segment-selector change one call.
3. **`vendor_dashboard_viewed` per distinct view** (WO-0112 text: per view change; CC9: per visit): recorded on arrival and on each change of segment selector, trend selector, category or filter, never per render (effect guarded by `viewKey`). React development double-effects are guarded by the same key.
4. **Component behaviour is tested without a browser** (no jsdom in the repo): the loaders are plain functions tested with a counting fake client; the markup of every state is tested through `DashboardView`; the effect wiring (once-per-view event, no arithmetic beyond the share) by source tests. The browser run is the screenshots.
5. **The smoke test `lib/vendor/dashboard.int.test.ts` is skipped unless the demo insights are loaded** (`seed-demo-insights.sh` says it is never run by a gate). It printed no SKIPPED when run seeded: 4 of 4 passed (vendor name via the grant, 6 calls, 150 users, Tops visible, Activewear not listed, every figure a multiple of 5, a filter hides segments as null, a consumer is refused by every view). In the gate it will be reported as skipped.
6. Contrast: `['accent', 'hairline']` added to the 4.5:1 pairs (bar fill on its track, both themes). Design tests: the module gets the same `cssProblems` rules and token check as `outfits.module.css`, plus 5 CSS mutants (radius, raw colour, shadow, 11px value text, gradient) in `design.test.ts`; nothing loosened. Component tests strip the module's hash from class names.
7. `git add -N` (intent to add, no content) was used to measure counted lines; the index was reset before the report. Nothing committed.
8. The local database held one stale `ops.vendor_query_log` row from an earlier run that makes 019 test 15 fail on a database that was not reset; the gate resets it. I did not touch it.
