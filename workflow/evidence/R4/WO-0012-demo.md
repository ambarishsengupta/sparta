## Defects and oddities seen while demoing (none fixed unless stated)
1. The app has no wishlist screen (R3 built none), so "Add to wishlist" can be confirmed only by the note, the disabled "On wishlist" button and the stored entry. Not in WO-0012's scope; reported.
2. The anchor id travels in the address (`/outfits?anchor=item-1`) to the app's own host on a hard load or typed URL. It is an opaque local id with no wardrobe attributes, and the work order asks for this address; a URL fragment (`#anchor=`) would never leave the browser. Reported, not changed.
3. `item_added` events made on the Wardrobe page carry `pair0` even when the pairing switch is on, because only the Outfits page loads the prior. The string is true to what was in use at that moment, but a reader comparing events may find it odd.
4. `next start` answered HTTP 500, not 404, for a `public/` file deleted after the server started (a development-environment effect); the app treats any non-OK answer as "prior off", so it made no difference to the page.
5. Occasion buttons stay disabled for a moment after the page opens while the wardrobe and the learned files load; a click in that moment does nothing (it happened twice in this run). With all switches off this is a few milliseconds.
6. Engine, not changed: Wardrobe unlock in the Office regular wardrobe shows three footwear entries that all claim the same count (80 new outfits), including Formal shoes although the wardrobe already holds some, so the panel gives little to choose between. The counts equal what the engine's own tests prove; I make no claim about usefulness.
7. The unlock panel's entry rows are drawn with the text at the top and the button centred (cosmetic; the screenshots show it).
