## What was built
- **Audit writer (new migration `20261112090000_wo0088_audit_log_writer.sql`)**: `app.write_admin_audit(p_admin uuid, p_action text, p_target text default null) returns bigint`, security definer, empty `search_path`, owned by postgres, execute for `service_role` only (revoked from public, anon, authenticated). It refuses (without writing) an id that is not an admin profile (42501 `forbidden`), an action that is not a lower-case dotted word of 2 to 4 parts (22023 `invalid_audit_action`) and a target outside the table's pattern, so no email, space or free text (22023 `invalid_audit_target`). It never reads the log back. pgTAP `014_wo0088_audit_writer.test.sql` (33 assertions). Existing tests extended, never loosened: 003 gains one assertion, the exact list of functions `service_role` can execute (the colour functions its catalogue writes already needed, plus the writer; plan 63 -> 64 per table); 008 gains one assertion that `service_role` can execute none of the argument-free functions (plan 205 -> 206).
- **Routes** (`app/api/admin/sources/route.ts` GET POST PATCH, `.../sources/[id]/takedown/route.ts` POST, `.../catalog/review/route.ts` GET POST), logic in `lib/server/admin-catalog.ts`, validation in `lib/admin-catalog.ts` (pure). Order of checks: backend must be Supabase (else 404), same-origin evidence for POST and PATCH (reuses `originAllowed`), session (401, 503 if the account service is down), role read from the database through `app.current_role()` (anything but `admin` is 403), body (max 20,000 characters, unknown keys refused), then one audit row, then the action. Fixed error texts from `lib/server/api.ts` (three codes added: `source_not_found`, `item_not_found`, `allow_refused`).
  - Sources: `site_url` https, or http on 127.0.0.1, localhost or [::1] only, no login part; `checked_on` a real date not later than tomorrow UTC; name 1 to 120 characters on one line; terms note up to 1,000; contact up to 200; take-down note up to 500. `allowed = true` is refused (422 `allow_refused`) unless `robots_allowed` is true, the terms note is not blank and the check date is present, tested against the stored row plus what is sent. A re-allow of a taken-down source clears `takedown_at` in the same update (the table's check refuses otherwise) and is audited as `source.reallow`; `takedown_note` is kept as history.
  - Take-down calls `catalog.take_down_source` with the person's own session (the function checks the admin role itself), so the items go and the source row stays with `allowed = false`.
  - Review: `activate` needs a category and sub-type pair of the taxonomy and only touches rows in `review`; `withdraw` sets `withdrawn`; any other row gives 404.
- **Proxy** (`lib/supabase/gate.ts`): a new gate state `admin` (role `admin`, email confirmed) whose home is `/admin/catalog`; `/api/admin/*` is let through in every state after the session refresh (the routes answer 401 or 403 themselves; a redirect to the sign-in page is no answer for an API client); the page `/admin/catalog` sends a ready consumer to `/`, and every other held state to its own gate page. The matcher needed no change (it already sends every non-static path through the proxy; `proxy-admin.test.ts` proves it for these paths).
- **Page** `/admin/catalog` (`components/admin/AdminCatalog.tsx`, `admin-actions.ts`): source register with Allow / Stop allowing, an add form, a take-down confirmation (names the source, says the items are deleted and cannot come back, the source stays as not allowed, asks for an optional note, acts only on "Confirm take-down"), the review queue with category and sub-type selects, "Make active" and "Withdraw". Classes and tokens from `globals.css` only; no brand name; `design.test.ts` and `contrast.test.ts` stay green.
- **Barcode lookup (FR-26)**: `lib/gtin.ts` (normalise, lengths 8, 12, 13, 14, pad to 14), `lib/barcode-lookup.ts`, `lib/barcode-scan.ts` (the camera scan with everything injected), `components/catalogue/BarcodeLookup.tsx` and `BarcodeScanner.tsx`, wired into the picker. Typed entry always; "Scan with camera" only where `BarcodeDetector` and `getUserMedia` exist, the camera starts only after the tap, `stop()` stops every track, ends the polling and detaches the stream (also when called before the camera answered), and the scanner's effect clean-up calls it on unmount. Only the text of a value that is a barcode number leaves the scan module; no frame is kept. The only thing sent anywhere is the padded code in the catalogue query (`CatalogueCollection.byGtin`, active rows, name then id, at most 20). One match opens the pre-filled picker form, several are listed to choose from, none shows the sentence with the padded code and "Add my own with this barcode" (`/items/new?barcode=` is read through `padGtin` again by the page). The code is saved in `app.items.barcode` in its padded form (`ItemInput.barcode`, `itemRow` keeps it only if it is 14 digits), for both a picked and a manual item.

## Decisions to check and deviations
- The audit row is written BEFORE the action (so a failed audit write stops it) and only for calls that pass validation; a call refused by validation or by the role check writes none. `source.create` has no target because the id does not exist yet. A take-down of an unknown id still leaves its `source.takedown|<id>` row. The page reads the register and queue after every action, so listing calls dominate the log.
- A new gate state `admin` changes the old behaviour in which an admin was held at "not available" like a vendor. No test asserted that for an admin. The consumer-side navigation bar still shows the consumer links to an admin (they redirect back to the admin page); not changed.
- `allowed = true` on a taken-down source is possible through the page's Allow button (re-allow, audited as `source.reallow`). The Data Sourcing Policy section 7 calls the taken-down row a marker that the source must not be collected again; the work order and WO-0083 notes say a re-allow clears `takedown_at`, so that is what is built. The owner may want a stricter rule.
- The takedown route is called with a body-less POST too (note optional).
- The bundled browser-only demo catalogue carries no barcode numbers, so lookup there always finds none (`byGtin` returns an empty list); barcode lookup works with the account-backed picker.
- The checkbox of the add-source form lays out a little awkwardly in the pane (label text under the box); not changed.
- Camera scanning itself was NOT exercised in the browser (it needs a camera and a permission prompt); it is covered by the fake-stream tests, and the browser run proved only that no `<video>` exists before the tap and that the control appears where `BarcodeDetector` exists.
